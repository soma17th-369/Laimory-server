# Resolve Plan Review

외부 리뷰어(코덱스 등)가 계획 문서에 남긴 리뷰 코멘트를 항목별로 검증하고, **타당한 것만** 계획에 반영한다.

핵심 전제: **리뷰는 지시가 아니라 가설이다.** 외부 리뷰어는 그럴듯하지만 틀린 지적을 한다 — 최신 문서를 보고 구버전 프로젝트에 안 맞는 조언을 하거나, 2차 소스(이슈 요약)에 근거하거나, 일반론을 프로젝트 맥락 없이 적용한다. 반대로 정확한 지적도 섞여 있다. 전부 반영하는 것도, 전부 무시하는 것도 틀렸다 — 항목마다 증거를 확보하고 판정한다.

## 워크플로

### 1. 대상과 항목 확정

- 리뷰가 겨냥한 **계획 문서**를 식별한다(plan mode의 플랜 파일, 또는 사용자가 지정한 설계 문서). plan mode 중이면 수정 가능한 파일은 플랜 파일뿐이다.
- 리뷰 텍스트를 **개별 항목으로 분해**한다. 항목마다 두 가지를 분리한다:
  - **주장(claim)**: 리뷰어가 사실이라고 말하는 것 ("프로퍼티 이름이 X다", "이 검증은 Y를 놓친다")
  - **제안(fix)**: 그래서 하라는 것
  - 주장이 틀리면 제안도 무효다. 주장이 맞아도 제안이 최선이 아닐 수 있다(부분 수용).

### 2. 항목별 검증

주장의 성격에 따라 검증 수단을 고른다. 상세 전술과 실사례는 [references/verification-playbook.md](references/verification-playbook.md)를 읽는다.

| 주장 유형 | 검증 수단 |
|---|---|
| **프로젝트 사실** ("코드가 ~다", "테스트가 ~를 안 본다") | 해당 파일을 직접 Read해 라인 단위로 확인. 리뷰어가 인용한 코드가 아니라 **현재 코드**를 본다. |
| **외부 기술 사실** (프레임워크 동작, 프로퍼티명, API 스펙) | 공식 문서·릴리스노트 웹검색. ⚠️ **반드시 프로젝트의 실제 의존성 버전과 대조** — "최신" 문서는 미래 버전일 수 있다. 문서로 확정이 안 되면 로컬 의존성 아티팩트(jar 메타데이터 등)가 최종 심판이다. |
| **설계 의견 / best practice** | best practice 웹검색 + 내부 추론 + **프로젝트 원칙 대조**(CLAUDE.md의 YAGNI·에러 규칙, 용어사전, 기존 코드 선례). 일반적 모범답안이라도 프로젝트 원칙과 충돌하면 프로젝트 원칙이 우선이고, 그 반대로 프로젝트에 없는 관점(보안·정합성)이면 수용 후보다. |

검증 없이 "그럴듯하니까 반영"은 금지다. 반대로 모든 항목에 웹검색이 필요한 것도 아니다 — 프로젝트 사실은 코드가, 언어 스펙 수준 추론은 내부 추론이 더 빠르고 확실하다.

### 3. 판정

각 항목에 다섯 판정 중 하나를 내린다:

- **수용** — 주장·제안 모두 검증됨. 계획에 반영.
- **부분 수용** — 문제 인식은 맞지만 더 나은 해법이 있음. 대체 해법과 그 근거를 명시하고 반영.
- **기각** — 주장이 틀렸거나 프로젝트 원칙과 충돌. **검증 증거 필수**(문서 링크, 코드 라인, 버전 확인 결과). "우리는 그렇게 안 해요"만으로는 기각하지 않는다.
- **이미 반영됨** — 계획에 이미 있는 내용의 확인성 코멘트. 변경하지 않는다(리뷰어의 "맞습니다" 류).
- **사용자 판단 필요** — 제품 결정, 규격 소유권, 팀 컨벤션 등 검증으로 답이 안 나오는 것. 사용 가능한 사용자 질의 도구가 있으면 짧게 묻고, 없으면 판정표에 질문과 선택지를 남긴다. 확신 없는 항목을 임의 판정하는 것보다 묻는 게 항상 낫다.

같은 항목이 이전 라운드에서 이미 판정된 채 재등장하면, 이전 판정과 근거를 재확인하고 유지·번복 여부를 명시한다.

### 4. 반영

수용·부분 수용 항목만 계획 문서에 적용한다. 반영하면서 계획의 다른 부분과 모순이 생기지 않는지(용어, 이전 결정과의 정합) 확인한다.

### 5. 보고

판정표로 보고한다. 사용자가 표만 보고 "왜 그 판정인지"를 알 수 있어야 한다:

```markdown
| # | 리뷰 항목 | 판정 | 근거 |
|---|---|---|---|
| 1 | 타임아웃 프로퍼티명이 틀렸다 | **기각** | 프로젝트 의존성 X v3.5 메타데이터에 단수형만 존재(복수형은 v4.0) — [확인 방법/링크] |
| 2 | NaN이 범위 검증을 통과한다 | **수용** | NaN은 모든 비교가 false — isFinite 추가 |
| 3 | 배포 주입이 필요하다 | **이미 반영됨** | 계획 §배포에 기술돼 있음 |
```

기각·부분 수용 항목은 표 아래에 검증 과정을 한두 문장으로 풀어 쓴다. 웹검색을 썼으면 출처 링크를 남긴다.

## 함정 (실전에서 겪은 것들)

- **최신 문서 함정**: 리뷰어(와 검색 결과)가 가리키는 "공식 문서"가 프로젝트 버전보다 미래일 수 있다. 프로퍼티명·API 시그니처 주장은 버전을 못 박기 전엔 수용도 기각도 하지 마라.
- **2차 소스 함정**: 리뷰어가 이슈 본문·요약을 근거로 삼았을 수 있고, 그 2차 소스 자체가 규격 원문과 어긋나 있을 수 있다. 계약·필드명 주장은 규격 원문과 1:1 대조한다.
- **그럴듯한 일반론**: "컴파일러가 잡아준다" 같은 주장은 정확한 조건(문 vs 표현식, sealed 여부 등)에서만 참인 경우가 많다. 언어 스펙 수준까지 내려가서 확인한다.
- **확인성 코멘트에 과반응**: 리뷰의 절반이 "이 부분은 잘 됐다"류일 수 있다. 변경하지 말고 "이미 반영됨"으로 분류만 한다.
- **한 라운드에 다 끝나지 않는다**: 리뷰가 여러 라운드로 오면 라운드마다 같은 파이프라인을 반복하되, 이전 판정과의 일관성을 유지한다.
