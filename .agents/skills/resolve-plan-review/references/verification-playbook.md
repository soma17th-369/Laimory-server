# 검증 플레이북

리뷰 항목의 주장(claim)을 유형별로 검증하는 전술과, 실제로 겪은 판정 사례. 사례는 이 레포의 지오코딩 enrich 계획 리뷰(2026-07, Epic #80)에서 나온 것이다.

## 전술 1 — 프로젝트 사실은 코드가 심판

리뷰가 "이 테스트는 X를 검증하지 않는다", "이 서비스는 Y를 주입받는다" 같은 프로젝트 사실을 주장하면, 리뷰에 인용된 diff/스니펫을 믿지 말고 **현재 파일을 직접 Read**한다. 리뷰 시점 이후 코드가 바뀌었거나, 리뷰어가 다른 브랜치를 봤을 수 있다.

**실사례 (수용)** — "PR2에서 서비스 생성자에 의존성이 추가되면 수동 `new`를 쓰는 기존 테스트가 깨지고, 순서 검증도 3단계뿐이다."
→ 해당 테스트 파일을 열어 정확한 라인(수동 생성자 호출, inOrder 3단계)을 확인했고 주장 그대로였다. **수용** — 계획의 테스트 섹션에 setUp 수정 + 4단계 순서 검증을 명시.

## 전술 2 — 외부 기술 사실은 "프로젝트 버전"이 기준

프레임워크 프로퍼티명, API 동작, 기본값 주장은 다음 순서로 검증한다:

1. 공식 문서/릴리스노트를 웹검색하되, **문서의 버전 표기를 확인**한다. docs 사이트의 "current"는 프로젝트가 쓰는 버전보다 미래일 수 있다.
2. 릴리스노트·이슈 트래커에서 "언제 바뀌었는지"를 찾는다. 개명·deprecation은 대부분 특정 버전에 기록돼 있다.
3. 그래도 확정이 안 되면 **로컬 의존성 아티팩트가 최종 심판**이다. 예: Spring Boot 설정 프로퍼티는 gradle 캐시의 `spring-boot-autoconfigure-<버전>.jar` 안 `META-INF/spring-configuration-metadata.json`을 직접 읽으면 그 버전에 존재하는 프로퍼티명이 정확히 나온다(zip을 in-memory로 열어 grep — 디스크 추출 불필요).

**실사례 (기각)** — "타임아웃 프로퍼티는 `spring.http.clients.*`(복수)다. 단수로 쓰면 안 먹는다. 참고: 공식 문서."
→ 리뷰어가 인용한 문서는 최신(4.x) 버전이었다. 프로젝트의 Boot 3.5.x jar 메타데이터를 직접 읽으니 `spring.http.client.connect-timeout`(단수)만 존재했고, 개명 시도는 GA 전에 롤백된 이력(spring-boot#45507)까지 확인됐다. **기각** — 리뷰대로 고쳤으면 오히려 타임아웃이 죽었다. 기각 근거(버전·확인 방법)를 계획에 남겨 다음 리뷰 라운드에서 재등장할 때 재확인 비용을 없앴다.

## 전술 3 — 설계 의견은 "취지"와 "해법"을 분리

best practice류 제안은 취지가 맞아도 제안된 해법이 최선이 아닐 수 있다. 취지를 인정하면 이 프로젝트/언어에서 같은 취지를 더 잘 달성하는 방법이 있는지 먼저 찾는다. 또한 `AGENTS.md`의 작업 원칙(YAGNI 등), `.agents/knowledge/codebase/interfaces/api.md`의 에러 계약, `.agents/knowledge/domain/ubiquitous-language.md`의 용어, 기존 코드 선례와 대조한다 — 일반론과 프로젝트 원칙이 충돌하면 프로젝트 원칙이 우선이다.

**실사례 (부분 수용)** — "타입 검증은 if 누적보다 switch가 안전하다. enum switch로 바꾸면 새 타입 추가가 컴파일에서 걸린다."
→ 취지(누락을 컴파일 타임에 잡자)는 맞지만 주장에 오류가 있었다: Java에서 enum 대상 switch **문(statement)**은 exhaustiveness를 강제하지 않는다(표현식·패턴 스위치만 강제, JEP 441). 이 프로젝트의 payload는 이미 sealed interface여서, **sealed 패턴 스위치**를 쓰면 문장으로도 컴파일 강제를 공짜로 얻는다. **부분 수용** — 리뷰의 해법(EnumMap+coverage test) 대신 패턴 스위치로 반영하고 대체 근거를 명시.

**실사례 (기각, 원칙 충돌)** — "반경·카테고리를 설정 프로퍼티로 빼고, 단일 구현이라도 인터페이스를 두자."
→ 튜닝 요구가 존재하지 않는 시점의 설정화·단일 구현 인터페이스는 `AGENTS.md`의 YAGNI 원칙("미요청 유연성·설정성 금지")과 정면 충돌. **기각** — 두 번째 구현이 실제로 생기는 시점에 추출하기로 계획에 명시.

**실사례 (수용)** — "좌표 검증에 `Double.isFinite`를 명시하라. NaN은 범위 비교를 빠져나간다."
→ 내부 추론으로 확인: NaN은 모든 비교 연산이 false라 `lat < -90 || lat > 90`을 통과한다. 웹검색 불필요, 언어 시맨틱만으로 판정 가능. **수용**.

## 전술 4 — 계약·규격 주장은 원문과 1:1 대조

필드명·payload 구조·API 계약에 대한 주장은 팀이 합의한 **규격 원문**(예시 JSON, 계약 문서)이 단일 기준이다. 이슈 본문·회의 요약·이전 세션 기록은 2차 소스라 규격과 어긋나 있을 수 있다 — 리뷰어도, 나도 2차 소스에 속을 수 있다. 규격 원문이 대화에 없으면 사용자에게 요청한다.

## 판정이 안 서면

- 두 해석이 모두 성립하거나, 제품/규격 소유권이 걸린 항목은 **사용자 판단 필요**로 분류하고 AskUserQuestion으로 묻는다. 선택지에는 각 판정의 트레이드오프를 요약한다.
- 검증에 시간이 드는 항목이 많으면, 먼저 전체 판정 초안(빠른 것부터)을 보여주고 무거운 검증(웹·아티팩트 확인)이 필요한 항목을 알린 뒤 진행해도 된다.
